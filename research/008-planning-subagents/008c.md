# Experiment 008C — Independent Patch Review

## Question

Can an independent small coding model correctly judge whether an already
committed candidate patch satisfies the requested runtime behavior, and how
does deterministic execution evidence affect that judgment?

## Motivation

Experiment 008B showed that explicit planning improved protocol validity,
preflight validity, and repository-file coverage without improving hidden
behavioral-oracle success.

Before adding another model call for repair or orchestration, Hewn should
measure whether an independent reviewer can reliably distinguish successful
from unsuccessful candidate patches.

Review and repair are intentionally separated.

## Frozen corpus

008C reuses committed patches from 008B implementation run 001.

Only committed patches are included because protocol and preflight failures
produce no candidate repository state to review.

Expected corpus:

- 6 direct committed patches;
- 8 plan-conditioned committed patches;
- 14 candidate patches total.

The runtime behavioral oracle from 008B is the frozen reference label.

Expected label distribution:

- 2 runtime-oracle PASS patches;
- 12 runtime-oracle FAIL patches.

The corpus is therefore strongly imbalanced.

## Important ground-truth limitation

The reference label is runtime-oracle success, not complete task correctness.

In plan-005, both candidate repositories pass the hidden runtime oracle while
also changing the visible explicit-TTL assertion incorrectly.

008C preserves those PASS labels because they were frozen by 008B.

The experiment must therefore use the terms `runtime_pass` and `runtime_fail`
rather than treating the oracle as a perfect complete-correctness label.

## Reviewer independence

The reviewer receives no planner output and no implementer response.

It receives only the task, original visible repository, candidate patch, and
the evidence allowed by the experimental condition.

This prevents the reviewer from merely agreeing with the reasoning that
generated the patch.

## Conditions

### A — patch_only

Reviewer receives:

- task;
- original visible repository;
- candidate diff.

No execution result is supplied.

### B — failure_signal

Reviewer receives:

- the same task;
- the same original visible repository;
- the same candidate diff;
- only whether deterministic runtime verification passed or failed.

No traceback, assertion, or execution output is supplied.

### C — execution_evidence

Reviewer receives:

- the same task;
- the same original visible repository;
- the same candidate diff;
- normalized deterministic execution evidence.

For failed verification, normalized evidence should contain mechanically
recoverable failure information rather than the complete raw pytest stream.

For passing verification, the evidence states that the hidden runtime oracle
passed.

## Reviewer output

The reviewer must return exactly one JSON object:

{
  "verdict": "accept" | "reject",
  "reason": "short concrete reason"
}

No repair is proposed.

No edits are allowed.

No tools are available to the reviewer.

## Frozen model controls

- Model: Qwen2.5-Coder-1.5B-Instruct Q4_K_M
- Temperature: 0
- llama.cpp context: 4096
- Maximum output: 256 tokens
- One reviewer call per candidate per condition
- No retries
- No protocol repair
- Strict JSON parsing
- No Markdown-fence stripping

## Primary metrics

Because the corpus is imbalanced, overall accuracy is not sufficient.

Report:

- protocol-valid rate;
- confusion matrix;
- runtime-pass recall;
- runtime-fail recall;
- balanced accuracy.

Where:

- accept on runtime_pass = true positive;
- reject on runtime_fail = true negative;
- reject on runtime_pass = false negative;
- accept on runtime_fail = false positive.

Balanced accuracy is:

(runtime-pass recall + runtime-fail recall) / 2

## Secondary metrics

Report:

- mean prompt characters;
- mean response characters;
- total reviewer inference time;
- verdict distribution;
- reason length.

Results should also be broken down by the original 008B condition:

- direct;
- plan_conditioned.

This breakdown is descriptive only.

## Interpretation boundary

A reviewer that correctly rejects a failing patch has demonstrated detection,
not repair.

A reviewer that receives a binary verification failure has not independently
discovered that execution failed.

Condition B measures whether a minimal deterministic execution signal is
sufficient for correct review classification.

Condition C measures whether detailed execution evidence adds value beyond
that signal.

Condition A measures semantic review from task, repository, and patch alone.

This is a 14-patch, temperature-zero diagnostic. It does not establish general
reviewer reliability.

## Decision rule

A reviewer stage should not be promoted merely because it produces plausible
explanations.

It must demonstrate useful discrimination on the frozen corpus.

If deterministic execution already supplies equivalent or stronger rejection
information, a model reviewer must provide additional diagnostic value that
justifies its inference and context cost.

Repair remains a separate experiment and is not part of 008C.
