# Experiment 008B — Plan-Conditioned Implementation

## Question

Does an explicit structured plan improve the behavioral success of a small
coding model on multi-step repository changes?

## Motivation

Experiment 008A measured planning quality but did not establish that a plan
helps downstream implementation.

A plan may improve scope discovery and coordination. It may also anchor the
implementer to incomplete or incorrect reasoning.

008B therefore measures implementation behavior directly.

## Conditions

### A — Direct implementation

The implementer receives:

- the task;
- the complete visible repository.

It produces one atomic edit batch.

### B — Plan-conditioned implementation

The implementer receives:

- the same task;
- the same complete visible repository;
- the frozen `source_plus_structure` plan produced in 008A run 002.

It produces one atomic edit batch.

No additional repository evidence is provided to the plan-conditioned
implementer.

## Why plans are replayed

The plans are replayed from the already-recorded 008A run rather than
regenerated.

This isolates the effect of conditioning the implementer on a specific
explicit plan from variation introduced by another planner generation.

The planner inference remains a real cost of the complete planned
architecture and must be included separately when reasoning about end-to-end
system cost.

## Frozen implementation controls

- Model: Qwen2.5-Coder-1.5B-Instruct Q4_K_M
- Temperature: 0
- llama.cpp context: 4096
- Maximum output: 512 tokens
- One implementer call per task
- No repair call
- Exact text replacements
- Maximum 6 edits
- Sequential batch simulation
- Atomic commit
- Deterministic preflight
- No model-visible execution feedback
- Same implementation prompt except for the explicit plan
- Same visible repository in both conditions
- Same hidden behavioral oracle in both conditions

## Test-edit boundary

Visible repository tests may be edited when required by the task.

The hidden `__hewn_oracle__` evaluation surface:

- is never shown to the model;
- cannot be targeted by an edit;
- is used only after deterministic preflight and commit.

This prevents modification of the evaluation oracle from being counted as
behavioral success.

## Outcomes

Primary outcome:

- hidden behavioral oracle success.

Secondary outcomes:

- implementation protocol validity;
- deterministic preflight validity;
- atomic commit rate;
- changed-file recall;
- changed-file precision;
- unnecessary changed files;
- diff additions;
- diff deletions;
- implementer prompt characters;
- implementer response characters;
- implementer latency.

## Interpretation

Correct plan scope is not equivalent to correct implementation.

A plan-conditioned implementation is successful only when the resulting
repository satisfies the hidden behavioral oracle.

A failed or misleading frozen plan is not corrected before implementation.
Planner anchoring is a competing hypothesis and part of the treatment being
measured.

This is an eight-task, temperature-zero diagnostic. Results do not establish
general coding-agent performance.

The experiment does not compare Hewn with frontier coding agents.

## End-to-end cost

The direct implementation path requires one model inference.

The planned architecture requires a planner inference plus an implementer
inference.

008B replays the frozen planner output to isolate plan conditioning, so the
planner inference is not rerun during the implementation experiment.

End-to-end analysis must therefore combine 008B implementation cost with the
already-recorded 008A planner cost rather than treating the plan as free.
